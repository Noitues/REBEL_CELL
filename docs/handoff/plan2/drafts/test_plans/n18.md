# test plan: N18 Data-driven rewards list

## 1. What is a rule here

**Rule-bearing (unit tests):**
- `reward_table_data.gd`: the `RewardTableData` and row resource, plus `validate()`.
- The row evaluator: condition matching, chance roll, count and pool draw. It is pure, with `RngService` and the context passed in.
- `netrun_session._finish_combat` and `_offer`: they build the offer list from the table and now hold no hard-coded offers.
- Banking of Rack rewards, including the `slice_flash` row kind. Its effect (the slice upgrade) is out of scope until the slice-upgrade pass; N18 tests only that the offer exists, is gated to Racks, and is drawn deterministically.
- Save and resume of a pending offer (the offer list is state and must round-trip).
- `content/config/reward_table.tres`: its content-lint tests.

**View glue (one flow test only):** the RewardList UI (`ui/` page). It renders the offers it is given and emits a pick. No rules live there.

## 3. Cases

2. `test_duplicate_row_id_rejected` – the error names "duplicate_row_id".

4. `test_empty_pool_rejected` – a pool kind with an empty pool gives "empty_pool".
5. `test_pool_references_missing_content_rejected` – "missing_content_id".
6. `test_count_zero_or_negative_rejected` – "bad_count". Count 1 is accepted.
7. `test_chance_out_of_range_rejected` – -0.01 and 1.01 give "bad_chance"; 0.0 and 1.0 are accepted.
8. `test_layer_range_inverted_rejected` – min 5, max 3 gives "bad_layer_range".
9. `test_tier_condition_out_of_range_rejected` – tier 0 and 5 give "bad_tier".
10. `test_flash_row_without_rack_condition_rejected` – "flash_needs_rack".

**test_reward_conditions.gd**
1. `test_node_type_filter_matches_only_listed` – a Router context against a Rack-only row gives no match.
2. `test_elite_flag_filter` – elite true and false.
3. `test_rack_flag_filter` – layer 4 optional Rack and layer 7 final Rack both match.
4. `test_tier_set_filter` – a row for tiers [3,4] matches 3 and 4, not 2.
5. `test_layer_bounds_inclusive` – min 4, max 4 matches layer 4 only. Layers 1 and 7 are the edges.
6. `test_empty_condition_matches_all` – an unconditioned row always matches.
7. `test_all_conditions_are_anded` – one failing condition gives no match.

**test_reward_roll.gd**
1. `test_chance_one_always_offers` – chance 1.0 over 100 seeds.
2. `test_chance_zero_never_offers_and_consumes_no_rng` – the stream position is unchanged.

## 4. Fixtures and helpers

- `tests/fixtures/reward_legacy_golden.json`: legacy offers keyed by (node type, tier, layer, seed). Capture it from the current code in a commit **before** the refactor.
- `tests/fixtures/reward_table_min.tres`, `reward_table_bad_*.tres` (one per rejection reason).
- `tests/helpers/reward_ctx.gd`: builds a context dictionary (node type, elite, rack, tier, layer) and a seeded `RngService`.
- The flow test follows the `bounded_wait.gd` conventions: bounded frames, a failure message naming the stage.

## 5. Existing tests likely to break

- `unit/test_w4_rewards.gd` and `integration/test_netrun.gd` / `test_netrun_extras.gd`: they assert the hard-coded offer shapes. Grep for `_offer`, `offers` and `_finish_combat`, and rebase them on the golden file.
- `integration/test_netrun_scene.gd`, `unit/test_parity_netrun.gd`: the RewardList row count.
- `unit/test_replay.gd`, `unit/test_simulation.gd`, `unit/test_balance_sim.gd`: the state hash or the RNG draw order may shift if `rewards` stream consumption changes. Re-baseline hashes only after the parity test passes.
- `unit/test_save_service.gd` (the integration one): the pending-offer field.
- `unit/test_content_registry.gd`, `test_suite_integrity.gd`: new files must be in the manifest.

## 6. Order

First, capture `reward_legacy_golden.json` from the untouched code. Then write `test_default_table_reproduces_legacy_router_offers`, together with the three validation cases `test_empty_pool_rejected`, `test_flash_row_without_rack_condition_rejected` and `test_duplicate_row_id_rejected`. Together they prove the refactor is behavior-neutral and that bad data is rejected before any UI work starts.
